# Forge IDE Manual (version 1.18.0)

Forge is a Cursor-style AI coding IDE that runs entirely on your Lenovo Googlebook 15. The editor, the agent, the terminal and the models all live on the laptop, and nothing you type leaves it. This manual explains every part of it.

## 1. The pieces

- **Forge IDE server**: a Python program in the Linux Terminal VM. It serves the editor and runs the agent, the tools and the terminal. It starts automatically with the VM.
- **Forge app** (version 3.2, native): the windows you open from the taskbar are a native Kotlin app, Kotlin from the window to the GPU engine service, no browser and no WebView anywhere, and it looks like the IDE you know: the top bar with the folder button and the search field (Ctrl P), the activity bar on the left (Explorer, Search in files, and the places for Source control, Run, Android, Notepads, History and Settings), the Explorer with file icons, file tabs, breadcrumbs and a code editor with syntax colors for fifteen languages, line numbers, a find bar (Ctrl F), go to line (Ctrl G), undo and redo, a bottom panel with tabs for the terminal (several shells as tabs, bash 1, bash 2 and so on), the agent log, problems, the debug console and the Googlebook's logcat with an app filter and levels, a real terminal emulator (colors, cursor movement, full-screen programs, 5,000 lines of scrollback, paste with Shift Insert), the AI panel with chat tabs, the model strip, Markdown replies with code blocks you can copy, tool cards, approvals, the vision model's cards with thumbnails, the thought process, Retry, image attachments and voice, splitters you can drag, a model picker in the top bar showing the model and its size (switch the engine or the model there), a status bar with Ollama, the GPU engine, memory and the index, a settings screen in the same style, and the Open folder dialog with recent folders. One window costs about 150 MB. It also hosts the GPU engine, the vision model and voice input. Forge itself runs inside the Linux Terminal, so when you open the app while the Terminal is closed, the app shows one steady waiting screen, opens the Terminal for you (its VM boots in about half a minute and starts Forge with it), checks every three seconds, and shows the IDE by itself as soon as Forge answers. Still to be built natively, in this order: code intelligence (hover, completions, diagnostics) in the editor, inline review of the agent's changes, the git panel, the Android and virtual device views, notepads, previews, the debugger and notebooks. Shortcuts: Ctrl S saves, Ctrl P finds a file, Ctrl Shift F finds in files, Ctrl L focuses the chat, Ctrl O opens a folder, Ctrl ` focuses the terminal, Ctrl B toggles the Explorer, Ctrl J toggles the bottom panel, Ctrl , opens Settings, Ctrl Shift N opens a new window.
- **Ollama with forge-coder**: your Llama 3.1 8B model, tuned for code, running on the CPU inside the VM.
- **Forge GPU engine**: the same Llama 3.1 weights on the Intel graphics, through llama.cpp's Vulkan backend, inside the Forge app.
- **The vision model**: Qwen3-VL, which looks at screenshots for Llama. It runs on the Intel graphics in the Forge app (the 4B build first, because it describes screens accurately; the 2B build is about 1.6 times faster at writing but invented errors on a terminal screenshot, and it is used only when the 4B build does not fit in memory), or on the CPU in the VM as a fallback. Text recognition (tesseract) reads the words in every image.
- **Helpers that start only when needed**: language servers for code intelligence, the debuggers, notebook kernels, a small embedding model for the codebase index, and whisper.cpp for voice input in a browser. Each one starts when you use its feature, only when memory allows, and stops again when it is no longer used.
- **Toolchains**: the Android SDK, Kotlin, Gradle, Java 21 and Rust, ready in Forge's terminal and for the agent (see section 15).

## 2. Starting and stopping

1. Open the **Terminal** app once after a restart so the Linux VM starts. It can stay in the background.
2. Click the **Forge** icon. If the VM is still booting you see a waiting screen that retries by itself.

From the Linux Terminal:

```
forge-ide status      shows whether the server runs, and the address
forge-ide start       starts it
forge-ide stop        stops it
forge-ide restart     restarts it (do this after editing its code)
forge-ide log         shows the last log lines
forge-ide open DIR    makes DIR the folder for new windows
```

## 3. Windows and folders

Every Forge window has its own folder, like a window in Cursor. The folder name is shown in the title bar and in the taskbar.

- **The search bar** (Ctrl P) finds files of this folder by name; a plain word also finds commands that match it, > lists every command, : goes to a line, and a path starting with / or ~ opens a file or folder anywhere. In a folder without files it says so.
- **Open folder** (Ctrl O, or click the folder name) switches this window to another folder. **New window** (Ctrl Shift N, or the button next to the folder name) opens another window. The Open folder dialog has a New window button, and every recent folder has a ↗ that opens it in a new window.
- Each folder keeps its own chats, AI Changes, open files, explorer state, project rules, memories and folder settings. The terminal of a window starts in its folder.
- A message that failed (the server refused it, or the run stopped with an error) gets a Retry button that sends the same message again with its attachments and mode; a refused message is replaced, a run that failed partway keeps what came back and the new attempt follows below.
- **The chat follows the reply**: while a reply streams in, the chat stays scrolled to its newest line, and so do the boxes inside it that have their own scroll bar (the thought process, the timeline). Scroll up to read something earlier and the view stays where you put it; a "Jump to the latest" button appears, and clicking it (or scrolling back down) attaches the view again. A failed command's output opens showing its end, where the exit status and the errors are.
- A chat always works in the folder it was started in. Opening a chat from another folder switches the window to that folder. A message you typed but did not send yet travels along when the window switches folders, and it also comes back after the window reloads; it is cleared when you send it or empty the box.
- **Several folders in one window**: the folder button with a plus at the top of the Explorer (or "Add folder to this window" in the command palette) adds another folder next to the project, like Cursor's multi-root workspaces. Each folder gets its own section in the Explorer, and quick open, search, replace and the agent's codebase search cover all of them. The ✕ on a folder's section removes it from the window; the folder itself is not touched. The list is saved in the project's `.forge/settings.json`.

## 4. The layout

- **Title bar**: folder name, new window, search (Ctrl P), the window's default model, and buttons for the sidebar, the terminal and the AI panel.
- **Activity bar**: Explorer, Search, AI Changes, Source control, Run and Debug, Android and toolchains, Notepads, Chats, Settings.
- **Editor**: the Monaco editor from VS Code, with code intelligence from language servers. Ctrl S saves. Ctrl \ splits the editor into two panes.
- **Bottom panel**: Terminal (several bash tabs), Agent log, Problems (with a count of errors and warnings), Debug console, Logcat.
- **AI panel**: the chat, with a tab for each open chat and, while a reply is written, a bar showing what Llama and the vision model are doing. Drag the gutters to resize; the layout is remembered.
- **Status bar**: engine state, free memory of the VM and of the Googlebook, the codebase index, files waiting for review, the debugger state, speed, context use, cursor position and the Tab completion state.

## 5. Working with the agent

Type at the bottom of the AI panel and press Enter (Shift Enter makes a new line). The mode menu next to the input box chooses how the agent works:

- **Agent** reads, searches, edits and runs commands until the task is done. Every command is shown first with Run, Always allow this chat and Skip. Edits are snapshotted and shown as file chips under the reply.
- **Ask** gives a plain answer with no edits.
- **Plan** investigates with read-only tools and writes a numbered plan first.
- **Custom modes** are your own modes. Choose "Edit modes…" in the menu, or open Settings, Custom modes. A mode has a name, instructions that are added to every message you send in it, a choice between all tools and read-only tools, and an option to run commands without asking.

The **model menu** next to the mode menu belongs to the chat, like in Cursor. "Default" follows the window's setting; you can also pick the GPU engine or any Ollama model for this chat only. Each chat remembers its choice.

Habits that help:

- **Thinking** shows the model's reasoning before each step.
- **Auto-run** lets the agent run commands without asking; destructive commands still ask.
- **Stop** with the red square or Esc. Type "continue" to resume after the step limit.
- **Code blocks** in replies have Copy, Insert at cursor and Apply to file with a diff review.
- **Verbose mode** (the V button) shows raw requests, tool calls, trimming and timing.
- Forge tells the model which file you have open and where the cursor is, so "this file" works. Only the name and line are sent, not the whole file, so prompts stay small.

## 6. Chat tabs, the queue and the to-do list

- **Tabs**: every chat opens in its own tab at the top of the AI panel, and several chats can work at the same time. The + button (Ctrl N) starts a new chat in a new tab. A pulsing dot marks a chat that is working, and a yellow dot marks one that finished or needs your approval while you were in another tab. Ctrl Tab switches tabs and Ctrl W closes the current tab while you are in the AI panel. Your open tabs come back when you reopen the folder.
- **Queue**: you can keep typing while the agent works. Enter adds your message to a queue above the input box, and queued messages are sent one after another when the reply finishes. Each queued message has Send now (stops the current reply and sends it next), Edit and Remove.
- **To-do list**: for bigger tasks the agent writes a to-do list at the top of its reply and ticks items off as it goes.
- **Chat history**: the clock button, or the Chats view, lists the chats of this folder, with a switch to see all folders. Open chats are marked with a dot.
- **Export**: the download button saves the chat as a Markdown file in Documents, in the Forge/Chats folder.
- **Restore checkpoint**: point at one of your earlier messages and click "Restore checkpoint". Forge undoes every file change made from that message onward, removes the later part of the chat, and puts your message back in the input box so you can change it and send it again.

## 7. Context and attachments

Type **@** in the input box (or click "@ Add context") for the context menu:

- **Files** and **folders** of the project (a folder adds its file list and its most relevant code).
- **codebase**: the most relevant code of the whole project, found by meaning and by keywords.
- **docs**: a documentation site you indexed (see section 18). "add new documentation…" indexes a new one.
- **chat**: the questions and answers of an earlier chat of this folder, without its tool output.
- **web**: web search results for your message.
- **git**: your uncommitted changes.
- **terminal**: recent output of the active terminal.
- **linter errors**: every error and warning from the language servers and the syntax checks.
- **notepad**: one of your notepads.

Typing @codebase, @web, @git or @terminal by hand works too. **Ctrl L** adds the editor selection, or the current file when nothing is selected.

**Attachments**: the 📎 paperclip button attaches files of any kind. Code, text and PDF files are read for the model (PDF text needs `pdftotext`), and images go to the vision model. Other files are saved, and the agent is told where they are, so it can process them with a command. You can also paste or drop files on the chat. Each attachment shows as a chip above the input box; the ✕ removes it.

**Slash commands**: type / at the start of the input box. Built in: /new, /reset (clears the model's context but keeps the transcript), /export, /plan, /ask, /agent, /review (reviews your uncommitted changes), /explain, /tests, /fix-lints and /summarize. Your own commands are Markdown files in `~/.forge-ide/commands`, in `.forge/commands` or in `.cursor/commands` inside the project; the file name is the command and the file's text is the prompt.

## 8. Screenshots and images

- **Paste** a screenshot into the chat box with Ctrl V, **drop** an image on the chat, or click the image button. PNG, JPEG, GIF and WebP up to 15 MB work. The image shows as a thumbnail; click it to see it full size.
- When you send, Forge reads the text in the image and asks the vision model to describe it. Llama gets both and answers. A panel "What the vision model sees in image 1" under your message shows exactly what Llama was told.
- Llama can ask the vision model its own follow-up questions with its look_at_image tool, for example what an error dialog says exactly. You see these as "Look at image" cards. It can also look at image files anywhere on the computer by path.
- On the GPU, Llama's engine pauses while the vision model looks, then resumes. A look took about a minute before version 1.17; Llama needs about 15 seconds to resume.
- Since version 1.18 the picture goes to the vision model scaled to 1,024 pixels on its longer side as a JPEG (640 image tokens; the model reads 32 by 32 pixel squares, and the encoder's work and memory grow with the square of the picture's patches, so a full 2880 by 1800 screenshot would have cost ten times the work for no better description), the vision server runs with a 2,048 token context, the description is asked for in at most 120 words and capped at 220 tokens, text recognition keeps the original at full size and runs on the VM's processor at the same time as the vision model instead of before it, and the vision server runs with flash attention off and the engine's automatic memory fitting off (the setting "Vision model: extra llama-server flags"), because inside the image encoder flash attention is the slow path on this kind of graphics, and the memory fitting refused to start once. Measured on 2026-10-19 with the 4B model on the graphics: 70 seconds for a full desktop screenshot (8 seconds loading, 13 seconds looking, 49 seconds writing 156 words), against 191 seconds and a broken stream before. If the vision server exits right after its launch, the app starts it again without the extra flags, then with the next model, and it keeps a foreground notification while the vision model works so Android cannot freeze the app in the middle.
- When there is not enough free memory for the vision model, Forge uses text recognition only and says so in the panel.
- The Images section in Settings chooses: auto (GPU, then CPU, then text recognition), gpu, cpu, or ocr (text recognition only).

## 9. Watching Llama and the vision model work together

Llama 3.1 cannot see images, so Forge pairs it with a vision model. You can watch every step in the chat.

- **The model bar** under the chat tabs shows what each model is doing right now while a reply is written, for example "Llama 3.1: Writing · 6.2 tok/s" or "Qwen3-VL 4B: Looking at the image · 12 s". A green dot means it is working, yellow means it is waiting or paused, and red means it failed or was skipped. Text recognition appears there too while it reads an image.
- **Conversation cards** show each exchange between the models. When you attach a screenshot, the card says "Forge asks Qwen3-VL 4B to describe image 1 for Llama 3.1". When Llama needs more detail, it says "Llama 3.1 asks Qwen3-VL 4B" with Llama's own question. The vision model's answer streams into the card word by word. The card shows the image, how long the look took and what text recognition read, and it ends with what Llama does with the answer.
- **"How the models worked"** at the top of a reply is a timeline of every step with its time. It covers Llama reading, thinking, writing and calling tools; text recognition; and the vision model starting, loading, looking and answering. It also shows the handoff of the Intel GPU: Llama's GPU engine pauses so the vision model can use the GPU, and it resumes afterwards. The title sums up how long each model was busy. The timeline is saved with the chat, so you can open it again later.

## 10. Voice input

Click the microphone button in the AI panel (or press Ctrl Shift Space) and speak. Click it again when you are done.

- **In the Forge app**, Forge uses Android's own speech recognizer, the same Google speech service the Googlebook uses elsewhere. You see the words appear while you speak, short pauses do not stop it, and it stops by itself after three minutes. The first time, Android asks whether Forge may use the microphone. The microphone also turns off when you minimize or close the Forge window.
- **Without the app's speech service**, Forge records your voice and whisper.cpp turns it into text inside the VM after you click the button again. This needs the voice part of `install-extras.sh`.

## 11. Editing

- **Code intelligence**: language servers give suggestions as you type, information when you point at a name, go to definition (F12 or Ctrl click), find references, rename (F2), formatting, quick fixes and live errors, for Python, JavaScript, TypeScript, shell, JSON, CSS, HTML, XML, C or C++, Kotlin, Java and Rust. A server starts when you open a file of its language and stops when the window closes. Settings, Editor, Language servers turns them off.
- **Ctrl K** on a selection: describe the change, review the diff, Ctrl Enter accepts, Esc rejects.
- **Tab completions** are off by default; Alt \ asks for one, and the Tab chip in the status bar turns them on.
- **Right-click** in the editor: Add selection to chat, Edit with AI, Explain, Fix problems. Right-click on a tab or a file in the Explorer: Open to the side.
- **Split editor**: Ctrl \ opens the current file in a second pane on the right. Each pane has its own tabs, edits show in both, and Ctrl S saves the file of the pane you are typing in. Ctrl \ again closes the split.
- **Markdown preview**: Ctrl Shift V in a Markdown file shows a live preview next to it.
- **Images** open in an image viewer. Click the image to switch between fitting the window and actual size.
- **Search and replace**: the Search view finds text in all files of the window (with a file filter and regular expressions). Type a replacement and click "Replace all". Forge shows how many matches in which files before it changes anything, and the change can be undone from AI Changes.

## 12. Reviewing and undoing

- **In the editor**: files the agent changed are highlighted like in Cursor. Added lines are green and removed lines are shown in red above them, with **Keep** and **Undo** buttons for each change. A bar at the bottom right shows the number of changes with ‹ and › to step through them, **Keep all** and **Undo all**. Undo puts the old lines back and saves the file; Ctrl Z brings the change back. The status bar shows how many files are still waiting for review; click it to open the next one. "Review in editor" under a reply starts a review of all files that reply changed.
- **File chips** under a reply open a side-by-side diff with Keep and Revert. **Revert all** under a reply undoes every file change of that reply.
- **Restore checkpoint** on your own messages undoes everything from that point on (see section 6).
- **AI Changes** lists the changes of this folder by request, newest first, with Revert all per request. "This folder" switches to "All folders". Replacements from the Search view appear here too. The changes are saved, so you can still review and revert them after Forge, the VM or the Googlebook restarts.
- Files the agent removes go to `.forge-trash` inside the project, or to `~/.forge-ide/trash` outside it. Nothing is deleted outright.
- Every save and agent edit runs a syntax check, and the language servers check open files as you type. Problems lists both, with Open, Fix with AI for each problem, and Fix all with AI.

## 13. Debugging

Forge debugs **Python, C, C++, Rust, Kotlin, Java, JavaScript and TypeScript** programs, and **Android apps** on a device. Open the **Run and Debug** view (the play icon in the activity bar).

1. Click left of a line number to set a **breakpoint** (a red dot), or press F9 on the line. Breakpoints are remembered per folder and move with the code when you edit.
2. Press **F5** (or Start debugging). Forge saves your files and runs the file you have open; you can type another file and arguments in the view. Forge picks the debugger from the file:
   - **Python** runs with debugpy.
   - **C and C++** are compiled first with debug information (`gcc` or `g++` with `-g -O0`, next to the source file) and run under GDB.
   - **Rust** is built with `forge-cargo build` and runs under rust-gdb, GDB with Rust's own display of strings, vectors and other types.
   - **Kotlin and Java** are compiled with the Kotlin compiler (and javac for Java files) into Forge's build folder, together with the libraries of the project, and run under the debugger built into JetBrains' Kotlin language server. Forge uses the Kotlin server the editor already runs for the folder; if none is open (in a Java project, for example), it starts one of its own for the session, which needs about 4.1 GB free on the Googlebook. The file needs a `main` function.
   - **JavaScript** runs with Node under Microsoft's js-debug (the debugger VS Code uses). **TypeScript** is compiled first with `tsc` into Forge's build folder (with your `tsconfig.json` when the folder has one), and breakpoints and the current line stay in your `.ts` files through source maps.
   The build output appears in the Debug console.
3. When the program stops, the line is highlighted. The view shows the **variables** (click ▸ to look inside lists, dictionaries, structures and objects), your **watch** expressions and the **call stack** (click a frame to jump there).
4. Step with **F10** (over), **F11** (into) and **Shift F11** (out). **F5** continues, **F6** pauses a running program, **Ctrl Shift F5** restarts and **Shift F5** stops.
5. The **Debug console** in the bottom panel shows the program's output. While the program is paused, type an expression there and press Enter to evaluate it in the current frame.

**Android apps.** In the Android view, Debug on device starts the installed debug build on the target device (a virtual device, the Googlebook or a paired phone) so that it waits for the debugger, connects through adb, and attaches the Kotlin debugger. Set breakpoints in your Kotlin or Java code first; the app stops there, with its variables and the call stack down into Android's own classes. Build and install the app before (Build, install and run does both). While attached to Android, expressions in the Debug console may not work yet; this is a known limit of JetBrains' debugger.

"Run without debugging" (Ctrl F5) runs the file with its output in the Debug console. The debugged program and its debugger run inside a memory cap (1 GB, or the Kotlin server's cap with a 256 MB Java heap for the program). `install-extras.sh debug` installs debugpy, GDB (C, C++ and Rust need GDB 14 or newer; Debian 13 has 16.3) and js-debug; TypeScript also needs `tsc` from `install-extras.sh lsp`. Stopping a session also stops the program and everything it started.

## 14. Notebooks

Jupyter notebooks (`.ipynb` files) open as cells, like in Cursor.

- **Code cells** have their own editor. Shift Enter runs a cell and moves to the next, Ctrl Enter runs it and stays, Alt Enter runs it and adds a new cell below. ▶ Run all runs every cell in order.
- **Output** appears under each cell: printed text, the value of the last line, tables (for example from pandas), images (matplotlib figures are shown automatically) and errors. An error has a **Fix with AI** button that sends the cell and the error to the agent.
- **Markdown cells** show formatted text; double-click to edit, Shift Enter to finish.
- Point at a cell for ▲ and ▼ (move), M or { } (switch between Markdown and code) and ✕ (delete). The toolbar adds cells, interrupts a running cell, restarts the kernel and clears all output.
- The **kernel** runs your code and keeps your variables between cells. The kernel menu in the toolbar chooses the language: **Python 3** (Forge's own kernel), **Kotlin** (JetBrains' Kotlin kernel, with Kotlin 2.4, data classes, collections and the Kotlin standard library) or **Bash** (your shell commands, with variables kept between cells). Any other Jupyter kernel installed into Forge's kernel folder (`~/.local/lib/forge-jupyter/venv`) appears in the menu too. The notebook remembers its kernel in the file, and its cells are highlighted in that language. `install-extras.sh kernels` installs the Kotlin and Bash kernels.
- A kernel starts when you run the first cell (the Kotlin kernel needs about 5 seconds), keeps running while the notebook is open (also across reloads), and stops after 10 minutes without an open window or 30 minutes without use. It runs inside its own 1.5 GB memory limit (the Kotlin kernel's Java heap is 640 MB), so a cell that uses too much memory stops the kernel instead of the system, and it starts only when that much memory plus the Googlebook's 2.3 GB reserve is free.
- The notebook is still a normal file: Ctrl S saves it with its outputs, and "{ } JSON" shows the file itself. "New Jupyter notebook" in the command palette creates one.

## 15. Android, Kotlin, Java and Rust

- **Toolchains**: the Android SDK (platforms 35, 36, 36.1 and 37.2 for Android 17; build-tools 35, 36.1 and 37; NDK 29; CMake 4.1.2; sdkmanager, avdmanager, lint, apkanalyzer, aapt2, d8, apksigner and zipalign), bundletool, the Kotlin compiler 2.4.21, Gradle 9.8.1, Java 21 and Rust 1.99 (cargo, clippy and rustfmt) are on the PATH in Forge's terminal and for the agent.
- **Code intelligence**: Kotlin (JetBrains' Kotlin language server, with its data sharing set to none, so it sends nothing), Java (Eclipse JDT), XML for AndroidManifest and layout files (LemMinX) and Rust (rust-analyzer) get suggestions, hover, go to definition, references, rename, formatting and live errors, like the other languages. `build.gradle.kts` files are Kotlin, and `build.gradle` files get Groovy highlighting.
- **The Android view** (the Android icon in the activity bar) shows the devices (section 16), the toolchains, Screenshot to chat and Logcat. In an Android project it adds Build, install and run; Build debug APK; Install; Run; App logcat; Lint; Unit tests; and Release bundle (AAB). In a Rust project it adds cargo check, build, run, test and clippy. Builds run in a terminal tab, so you can watch them and stop them with Ctrl C.
- **Devices**: your Googlebook, virtual devices with Android 11 to 17 in every screen shape, and devices paired over Wi-Fi (section 16). Forge uses Debian's adb, the same one your other Googlebook tools use, and installs apps with `adb install` instead of Gradle's installDebug, because a second adb version could stop the adb server those tools rely on.
- **Compose previews without a device.** In an Android project with Jetpack Compose, Compose previews (in the Android view, next to each app module) or `forge-preview [:module]` in a terminal renders every `@Preview` of the module as a picture, the way Android Studio's preview pane does, on six screen shapes: phone, foldable, tablet, round watch (454 by 454 pixels, with the round screen), square watch and TV (1920 by 1080). Wear OS previews are real Wear OS Compose screens, so this is how you check a Wear OS app's screens here (see Devices). Choose shapes with `--shapes watch-round,tv`, for example. The pictures land in `~/.forge-ide/previews/<project>/<date and time>/<shape>/`, one per preview, named after the function and its preview group, and the terminal lists them; open them in the editor or attach them to the chat for the vision model. How it works: Robolectric runs Android's own framework on the computer and Roborazzi saves each screen as a PNG. Forge adds its test and the libraries it needs (Robolectric 4.17, Roborazzi 1.76 and ComposablePreviewScanner 0.9.3) through a Gradle init script for that run only, so your project's files are not changed, and Compose's test libraries follow the Compose version your project already uses. A preview's own background is used, and watch screens are black otherwise. The run gets the Googlebook's free memory above its 2.3 GB reserve as a hard cap (at most 3.5 GB, at least 2.8 GB, so it needs about 5.1 GB free), and the first run downloads Android's framework for Robolectric once. A run on a small project takes about 20 seconds after that.
- **Screenshot to chat** attaches what the target device shows, so the vision model can look at your running app for Llama. The agent does the same by itself in Android projects: it builds, installs and starts the app, takes a screenshot, asks the vision model what the app shows, and reads the error log.
- **Logcat** in the bottom panel shows the log live, colored by level, for the whole device or one app, with a text filter and Add to chat. It stops by itself after 15 minutes or 20 MB.
- **Builds and memory**: `forge-gradle` and `forge-cargo` (used by the Android view, and applied automatically to the agent's Gradle, Cargo and kotlinc commands) size every build to the free memory. A Gradle build gets the Googlebook's free memory above its 2.3 GB reserve as a hard cap (at most 2 GB, at least 1.5 GB, so it needs about 3.8 GB free), and Gradle's Java heap is scaled to fit well inside that cap, so a build that needs more memory stops with Gradle's own message instead of being killed. Builds run without a lingering Gradle daemon, so their memory is returned as soon as they finish; `FORGE_GRADLE_DAEMON=1 forge-gradle ...` keeps the daemon for faster repeated builds. `~/.gradle/gradle.properties` also limits Gradle when you run it yourself: a 1 GB heap, Kotlin compiled inside the Gradle process, two workers, and a daemon that stops after 15 idle minutes. Cargo uses three parallel jobs.
- **Language servers for Kotlin, Java and Rust** are large programs. Each starts only with enough free memory and runs inside a memory cap: on the Googlebook, 3.8 GB free for Java and Rust, and 4.1 GB for Kotlin (4.7 GB in an Android project, because indexing android.jar takes more memory).
- **The Kotlin project model** (Settings, Editor). JetBrains' Kotlin server normally runs a Gradle import every time it starts in a Gradle project, which adds a second large Java process. In **light** mode Forge writes the project description itself, in its own cache folder (your project is not touched): the source folders of each module, the JDK, the Kotlin library, android.jar and the app's R class (after one build) for Android modules, generated sources, jars in libs folders, and the libraries your build files name when Gradle has already downloaded them. Android's own sources are left out to save memory, so hover documentation for Android's own methods is shorter. The server then needs about half the memory and starts in seconds, with full error checking, also for loose Kotlin files. **gradle** mode uses the full Gradle import, with every library exactly as Gradle resolves it, and needs 4.7 GB free (5.5 GB in an Android project). **auto** (the default) uses the Gradle import when there is room for it and light mode otherwise. If light mode reports a library as missing, build the project once (so Gradle downloads it) or switch to gradle mode. When memory is short, Forge says so once, and the server starts when you reopen the file later with more memory free.

- **Kotlin Multiplatform.** In a multiplatform module (one that applies `kotlin("multiplatform")`), Forge's project model makes every source set its own module, linked the way the Kotlin plugin links them: jvmMain, androidMain and the others build on commonMain, iosArm64Main builds on iosMain, appleMain and nativeMain where they exist, and test sets see their main sets. So `expect` declarations in commonMain and the `actual` ones in each platform set link up (Go to implementation on an `expect` lists every `actual`), Android APIs resolve only in Android source sets, and code in commonMain that uses a platform API is reported as an error. Forge always uses its own model for multiplatform projects, because the Kotlin server's Gradle import does not support them yet. JavaScript, Wasm and iOS source sets are checked as shared Kotlin, but their platform APIs (the browser, UIKit) are not known to the Kotlin server, and a missing `actual` is not reported yet. The Android view adds a Kotlin Multiplatform section with Check common code, Build JVM, JVM tests, Build desktop, Run desktop app (Compose Multiplatform, in the Linux VM's display), Build Android, Run in browser (JS or Wasm) and All tests, each a forge-gradle task in a terminal. iOS and macOS targets can only be compiled on a Mac with Xcode.
## 16. Devices and virtual devices

Forge works with three kinds of devices, and one of them is always the **target**. Build, install and run, Logcat, Screenshot to chat, and `adb` in Forge's terminal and in the agent's commands all go to the target device. You choose it with Use in the Android view, or with `forge-device use <name>`.

- **This Googlebook** (Android 17), over Wireless debugging. Forge only shows its screen. It never taps or types on it, because it is the screen you are working on.
- **Virtual devices**: real Android 11, 12, 13, 14, 15, 16 and 17 running in containers inside the Linux VM, plus Android 17 with Google apps, Android TV 16 with Google apps, and Google's own official builds of Wear OS 6, Google TV 16 and Android 16 with Google Play (Google's Pixel-style Android). The VM has no hardware virtualization, so Google's emulator cannot run here. A container runs Android directly on the VM's Linux kernel instead, the way Android's cloud test farms do. Android 11 to 16 come from the open-source Redroid project. The others are LineageOS builds made for containers by the WayDroid-ATV project: Forge downloads them, checks them against the project's published checksums and packages them with `forge-vd-image 17`, `forge-vd-image 17-google` and `forge-vd-image tv16-google`.
- **Device personas**: a virtual device dressed as a specific Galaxy, Pixel, OnePlus, Motorola, Lenovo, Xiaomi, Fire TV or Shield (see below).
- **Device labs**: real phones, tablets and watches with the makers' own software, in Google's and Samsung's labs (see below).
- **Phones, tablets, watches and TVs paired over Wi-Fi**, for example your Galaxy phone with One UI, a Galaxy Watch, a tablet or an Android TV.

**Virtual devices.** In the Android view, under Virtual devices, download an Android version once (Android 17 is a 1.4 GB download, the others about 0.7 GB). Then choose the version and a type (phone, small phone, foldable, tablet, round watch, square watch, TV or desktop) and click Create. Each device keeps its own data, so installed apps and settings stay between runs. Stop ends it. Forge always stops a device from outside and never uses Android's own power off (see Memory safety).

**The device window.** Screen opens a floating window with the device's live screen, about two pictures a second. Click to tap, hold to long press, drag to swipe and scroll the wheel to scroll. Click the screen and type to send keys: Escape is Back, and Enter, Backspace, Tab and the arrow keys work. You can also type into the text box and press Enter. **What the types mean.** A TV device runs Android's television mode: the TV features are declared, apps get the television UI mode, and Forge starts TV apps through their Leanback launcher entry. On Android 11 to 17, watches are watch-sized round or square screens of phone Android. For a real watch, choose Wear OS 6 (below), which is Google's own Wear OS, and for Google TV choose Google TV 16. Compose previews (section 15) also render your Wear OS Compose code on round and square watch screens without any device.

**Android with Google apps, and Google TV.** Android 17 with Google apps has the Play Store, Play services and Google's apps, so you can test sign-in with Google, Play services APIs and in-app purchases flows. Android TV 16 with Google apps is a real Android TV with the Play Store, Google Play services and the Google Assistant for TV, and it is ready about 50 seconds after Start. Its Google TV home screen is switched on in the TV's own Settings, on the Waydroid options page (Google TV mode). Stop and start the device afterwards, because the switch takes effect when Android starts. Signing in to Google Play may first need the device registered as a test device at google.com/android/uncertified, because these community builds are not certified by Google. The Google apps come from the WayDroid-ATV project, not from Google directly.

**How Android TV 16 runs here.** This build is older than WayDroid's support for container engines like Podman, and it expects the container that WayDroid's own app sets up. Forge provides the same pieces:
- a small start program, `forge-init`, runs inside the container just before Android. It gives Android a fresh `/dev` with copies of the graphics, terminal and loop devices (opened to Android's own users, as WayDroid does, but never the VM's disks), Android's three binder devices in a private binder file system, and a private terminal file system. It also moves Android into its own control group, so Android can organize its processes there;
- Forge writes the settings file that WayDroid's app writes (the graphics drivers, the device type and a persona's identity);
- Android's network service asks for its address by DHCP, as a TV does at home. Forge gives each TV device a fixed address on Podman's network and runs a small DHCP and DNS service (dnsmasq, which is already part of the VM) while a TV device runs. It listens only on Podman's network, answers only Forge's TV devices, passes name lookups to the VM's own resolver, and stops with the last TV device. `sudo systemctl status forge-vd-dhcp` shows it.

**Google's own Wear OS, Google TV and Pixel-style Android.** Three versions are Google's own official builds for x86 computers, the same software Google's Android Studio emulator runs:
- **Wear OS 6** (Google's Wear OS 6.0, Android 16), for round and square watches. It is what the Pixel Watch 4 and Galaxy Watch8 run. You get Wear OS's own watch face, system interface, tiles, settings, notifications, Health Services and Play services for Wear, so you can install and test real Wear OS apps, tiles and watch faces. It is ready about 12 seconds after Start (the watch face appears within about 45 seconds, once Wear's welcome screen is done) and uses about 0.9 GB of memory.
- **Google TV 16** (Google TV on Android TV 16), for TVs, with Google TV's own home screen, the Play Store and Google Play services. On the first start, Google TV asks whether to set it up with a Google account; choose Cancel to use it as a basic TV.
- **Android Automotive 15 with Google Play**, for the car device type (a 1408 by 792 car display, as in Google's own car emulator), with Google's car launcher, the Play Store for cars and Google Assistant; **Android Desktop 14**, Google's desktop form of Android for the desktop window type; and **Android XR 14** (Google's XR developer preview) for the XR headset type, whose image needs Google's separate developer-preview license accepted once with `sdkmanager --licenses` before Download works. These three were built on 2026-10-16; their first boots are being verified and the manual will record the results.
- **Android 16 with Google Play**, for phones, small phones, foldables, tablets and desktop windows. This is Google's Pixel-style Android: the Pixel Launcher with the At a Glance date and the Google search bar, Google's own system interface, Android System Intelligence, the Play Store, Play services, Chrome, Gmail, Photos, YouTube and Google's Phone and Messages apps. It is ready in about 20 seconds and uses about 1.9 GB.

Download each once under Virtual devices (1.1 GB, 1 GB and 1.9 GB from Google's SDK repository; Google's own sdkmanager checks them against Google's checksums). Unpacked and prepared, they take about 6.5 GB, 12 GB and 9 GB of disk space. Google's emulator needs hardware virtualization, which this computer's VM does not have, so Forge runs Google's system on the same container base as Android 11 to 16:
- Google's system, product and system_ext partitions are used as Google ships them, including all of Google's system packages (APEX modules) and apps, with Redroid's Android 16 vendor partition (graphics, network and audio for containers) in place of the emulator's;
- Redroid's start program and SELinux library, which are made for containers, take the place of Google's. They never load Android's SELinux policy into the VM's kernel, and the VM shield still stands behind them;
- Google ships most system packages compressed, and Android would check a security label on each one when it unpacks it on the first start. Forge unpacks them once when it builds the image, the same way;
- `forge-init` (a small start program) gives Android its own cgroup branch, owned by Android's system user as on a phone (Android needs that to place sandboxed processes such as WebView's and Chrome's), and the same device-mapper lock as Android TV 16;
- `libforge_compat.so`, a small library loaded into Android's process starter, answers two questions a container cannot: the SELinux labels Google's connectivity module checks on its BPF files (a kernel without an SELinux policy has none), and the owner change Android makes on a sandboxed process's cgroup folder. Every other call goes to Android unchanged;
- before Android's network loader runs, the container gets private stand-ins for two network settings that only exist in the VM's own network namespace, so the loader's writes stay in the container;
- watches report a full battery on mains power (Wear OS waits for 20 percent before it starts), Wear's setup wizard, which waits to pair with a phone, is skipped, and a round watch tells apps that its screen is round, as a real one does.
Phone pairing, the Wear OS companion app and the watch's sensors are not there, because there is no phone or hardware; for those, use a paired watch or a lab watch.

**Emulated ARM devices: the makers' own Android.** The makers build One UI, OxygenOS, ColorOS, HyperOS, MagicOS, Nothing OS, OriginOS and Realme UI for ARM processors only, so on this x86 computer they run through ARM emulation. QEMU emulates an ARM64 computer in software (the Linux VM has no hardware virtualization), which runs a LineageOS virtual machine made for QEMU by the android-lineage-qemu project, and that machine boots a maker's system image from a third disk through its own boot menu. The system images are community ports from the Mystic GSI project ("GSI" images that run on any Treble device), downloaded from the project's SourceForge files; they are the makers' real system software, repacked by the community, not releases from the makers. In the Android view, under Virtual devices, the makers' systems are listed as "(ARM, emulated)". Download one (3 to 7 GB, plus 1 GB for the virtual machine once), create a device and start it. What to expect, measured on this Googlebook:
- it is slow. A full ARM Android takes 15 to 30 minutes to its first screen, the emulated clock runs at about a third of real time, and the screen updates a few times a second; Screen in the device window shows the emulated display from the first second, even before Android is up;
- it runs inside a 3.5 GB memory cap and a four-core CPU quota, with a four-hour limit, and needs 5.9 GB free on the Googlebook to start;
- taps, swipes and keys in the device window go through the emulator itself until Android's adb is up (adb starts once the boot is complete), so the setup wizard can be worked from the first screen;
- Forge prepares each image once, with `bin/forge-arm-image` (the markers in `~/.forge-ide/vd/arm/gsi/<version>/` say which preparation version an image has; an older one is prepared again on the next download request, without downloading again). The preparation adds Forge's adb key and its own copy of adbd on the forwarded port from the moment `/data` is mounted, a log service that writes Android's whole log to the device's `serial.txt` in `~/.forge-ide/vd/arm/devices/<device>/` (where a boot that stops can be read), and Android's timeout multiplier (30; the watchdog, "isn't responding" and binder timeouts all stretch with it, because the makers' system servers start hundreds of services on an emulated CPU and OxygenOS's needed more than the ten minutes a multiplier of 10 allows). Most ports are "user" builds whose SELinux policy keeps init from starting anything in the `su` domain, and the makers' systems read their own vendor properties, which the virtual machine's vendor partition labels as plain vendor properties that the system may not read (OxygenOS's zygote died at every start without one). Forge therefore appends its rules to every system policy file the port has (the ports compile their policy at boot; OnePlus's init uses the "debug" policy files from `system_ext`, hence every file, and in some ports `system_ext` and `product` are links that Forge follows) after a test compile on this computer with `secilc`, and gives every file it adds a proper SELinux label with `setfattr` (a file copied in from Linux has none, and Android's processes may not open an unlabeled file). The rules come in two sets, and an image prepared with only the first gets the second on its next preparation: the first lets init start services in the `su` domain and lets every domain read the vendor properties; the second (preparation v11, 2026-10-18) lets adbd become root (a user build's policy forbids that transition, and Forge's root adbd died at once on HyperOS) and lets the system server and the camera service write vendor properties (HyperOS 3's system server died at every start on a camera property write until the device rebooted into recovery);
- OnePlus's, OPPO's and Realme's ports (the Oplus group) leave out a feature library that their netd extension opens at start, and netd crashes without it, which restarts zygote every ten seconds for ever; Forge installs a stand-in library that does nothing (`vd/oplusnetd-stub.c`) in its place;
- the preparation also sets three more properties for every port: `ro.hw_timeout_multiplier=30` (above), `pm.dexopt.first-boot=extract` with its two siblings (so the first boot does not spend an hour verifying the bytecode of every preinstalled app; classes are verified when first loaded), and `ro.mediaserver.64b.enable=1` (OxygenOS's media service is a wrapper that runs the 64-bit media server only with this property; without it the wrapper exits every few seconds, and its restarts keep the software codec service from registering, which later aborts the system server); Forge's own adbd also stops Android's own adbd whenever that comes up, because two adbd on the same port leave adb "offline"; the preparation also gives the emulated machine its network address at the start of the boot (Android's own Ethernet service does that late, at the very end on ColorOS, and the forwarded adb port reaches the machine only once the address exists), and it patches one method in the system server (`vd/patch-permission-write.sh`, with the smali tools): on an emulated CPU the server's delayed "write settings" message fires while the new permission service is still reading its saved state, the write dies with "lateinit property state has not been initialized", and the system server crashes at every boot after the first (seen on OxygenOS and ColorOS); the patch lets that one write fail quietly, and the next write repeats it once the state exists. The original jar stays next to the patched one as `services.jar.before-forge`;
- the emulated display has no EDID (every mode is 60 Hz), and Forge watches the display's size every 20 seconds while the device runs: OxygenOS's refresh-rate service asks for an exact 60 Hz mode ten minutes into the boot, the only exact-60 modes the virtual display offers have other sizes, the system switches to 640x480, the virtual display cannot scale, and every frame then fails until Forge switches it back to its real mode;
- Samsung's One UI needs two more pieces, which Forge adds to the image: Android's standard key store in place of Samsung's (Samsung's demands a hardware feature the virtual machine's KeyMint does not have and stops instead of coping), and a stand-in for Samsung's own health service, `forge-sehhealth`, which hangs off the standard health service as a binder extension and answers Samsung's battery service with empty results. Status on 2026-10-16: Nothing OS 4 (Android 16) boots to its setup wizard through Forge in about 50 minutes the first time and 6 minutes after that, and Forge then shows it Ready with adb working (verified with screenshots and over adb); Samsung One UI 8 boots to Samsung's own setup wizard in 31 to 60 minutes, through Forge's own device as well (verified with screenshots on 2026-10-16, after Forge's additions: the standard key store, the health stand-in with Samsung's battery callback, an empty stand-in for Samsung's display-quality service, Android's timeout multiplier set to 10 (30 since 2026-10-17, see above), and Samsung's boot checker kept off, because it crashes the kernel on purpose when a boot takes longer than it expects); OnePlus OxygenOS 16 boots to its own setup wizard through Forge's device (verified with a screenshot on 2026-10-17, Ready after 17 minutes on its second boot; its first boot took about an hour, and it needed every one of the preparation steps above: the policy rules, the stand-in network library, the timeout multiplier of 30, the skipped bytecode verification, the 64-bit media server, Forge's own adbd alone on its port, and the display guard); OPPO ColorOS 16 boots to a running Android through Forge's device (boot completed, adb working, Ready after about 30 minutes on 2026-10-17, after the same preparation plus the system server patch), but its home screen stays black (the launcher's task is hidden in SurfaceFlinger while the window manager reports it drawn), and its system server died again a few minutes after the boot completed, so it is not usable yet; Xiaomi HyperOS 3 boots to its lock screen through Forge's device (boot completed in 13 minutes, screenshot taken on 2026-10-18) after one more preparation step (its system server died at every start on a vendor property write that the policy forbade, until Forge's second rule set allowed it), but adb to it stops a few minutes into the boot, when HyperOS's Ethernet service clears the address Forge set and Forge's adbd inside the device never serves another connection; the preparation now carries a small watchdog service (`forge-adbwatch.sh`) that starts adbd again when the address changes or connections pile up, and that watchdog has not been verified in a boot yet. Honor MagicOS 10, vivo OriginOS 5, Realme UI 7 and the Pixel Android 17 port are downloaded and prepared the same way but have not been booted yet, and OPPO ColorOS 16 stays unusable as described. I stopped the maker-by-maker testing here (each boot takes an hour on an emulated CPU, and every maker so far needed its own fixes), and the preparation script, the boot logs in `serial.txt` and the notes in this manual are there for anyone in the Googlebook community who wants to take a maker further. Android's own "isn't responding" dialogs appear on these devices because of the slowness; choose Wait.
These are research-grade devices for seeing the makers' real software; for everyday testing of your app's behavior on those devices, a persona on native Android is fast.

**Device personas.** For everyday testing, a persona reproduces what your app actually meets on a maker's device on fast, native Android. Choose a persona when you create a virtual device (or `forge-device new 16 --persona galaxy-s25`; `forge-device personas` lists them). A persona device gets:
- the device's screen: its pixel size and density (so the same layout in dp), its camera cutout with the status bar height that follows from it, its rounded corners in the device window, and its navigation mode (gestures or three buttons);
- its identity: `Build.MANUFACTURER`, `BRAND`, `MODEL` and `DEVICE`, so code that checks for a maker takes that branch;
- its features, for example Fire TV's `amazon.hardware.fire_tv`, Samsung's experience flag, or a round screen for watches (`isScreenRound()` is true);
- its maker's battery behavior on request (below).

There are 28 personas: Pixel 10, Pixel 10 Pro XL, Pixel 10 Pro Fold (open and closed), Pixel Tablet and Pixel Watch 4; Galaxy S25, S25 Ultra, A56, Z Fold7 (open and closed), Z Flip7 and its FlexWindow, Tab S11 and Galaxy Watch8; OnePlus 13, 13R and Open; Moto Edge 2025, Razr+ 2025 (open and its cover screen) and Moto G 2025; Lenovo Legion Tab Gen 3 and Yoga Tab Plus; Xiaomi 15; Fire TV Stick 4K Max, Google TV Streamer and Nvidia Shield TV Pro. Screens marked exact come from Google's, LineageOS's or Amazon's published device data; the others (most Samsung, Motorola, Lenovo and Xiaomi cutouts and densities) are close approximations, labeled so in the list. A persona is labeled as one everywhere, because it is Android with that device's screen, identity and behavior, not the maker's own interface: One UI's own menus, Samsung's notification style and the makers' system apps are not there. Custom cutouts need Android 14 or newer (tested on Android 16, on Android 17 with Google apps, and on Android 16 with Google Play as a Pixel 10); on older versions the rest of the persona still applies. Personas are most real on Google's own builds: the Pixel personas on Android 16 with Google Play get the Pixel Launcher and Google's apps, the Galaxy Watch8 and Pixel Watch 4 personas on Wear OS 6 are real Wear OS with that watch's screen and identity, and the Google TV Streamer persona on Google TV 16 has Google TV's own home screen.

**Maker battery behaviors.** The biggest difference between makers for most apps is how hard they kill apps in the background. In the device window of a virtual device, choose a behavior, enter your app's package (Forge fills in the open project's) and click Apply, or run `forge-device behave <behavior> <package>`. The behaviors are made with Android's own controls (`am`, `cmd appops`, `dumpsys deviceidle`): Samsung's sleeping and deep sleeping apps, OnePlus's deep optimization, Xiaomi's autostart block, Motorola's inactive app killing, Lenovo's swipe kill, and Doze now. Reset the app to normal undoes them. Then use your app, check that its work, alarms and notifications still happen, and read Logcat.

**Device labs: the makers' real software.** For the real One UI, OxygenOS, My UX or Pixel UI, Forge connects real devices. The Device labs section of the Android view has three:
- **Google's device lab**, through Google's Android command line tool, which is installed in the Linux VM. It has real Pixel phones up to the Pixel 11 on Android 17, a Pixel Tablet and a Pixel Watch, about 70 Samsung Galaxy phones and foldables, about 20 Motorola phones, and OnePlus, OPPO, realme, Xiaomi, Sony and Nothing phones. **Pairing over Wi-Fi.** On the device, open Settings, Developer options, Wireless debugging, Pair device with pairing code. **From the terminal and for the agent**, `forge-device` does all of this. `forge-device` alone lists the devices. **Two adb servers.** The Googlebook stays alone on the shared adb server (port 5037), because your other Googlebook tools use a plain `adb shell` there, and a second device would make them fail. Virtual and paired devices are on Forge's own adb server (port 5041). In Forge's terminal, `adb` goes to the target automatically. With `-s` or `-P` you choose the device or server yourself.

**Removing a virtual device.** Forge never deletes devices or downloads by itself. A device's Android data lives in the volume `forge-vd-<id>-data`, and its container is named after the device and its protected image. Devices on Android 11 to 16 keep their container between starts. When a protected image changes, the device gets a new container on its next start and keeps its data; the older container stays stopped (`old_containers` in `~/.forge-ide/vd/devices.json` lists them) until you remove it with `sudo podman rm <name>`. The WayDroid-ATV builds (Android 17, Android 17 with Google apps and Android TV 16) start from a fresh container every time, which Podman discards when the device stops, because WayDroid's start step damages a reused container on its second start (it deletes `task_profiles.json`, and Android's storage service then refuses to start). Their data stays in the volume as well. To remove a whole device, stop it, run `sudo podman rm` for its containers and `sudo podman volume rm forge-vd-<id>-data` in a terminal, and remove its entry from `~/.forge-ide/vd/devices.json`.

**Updates and upgrades of the images (version 1.15).** Every emulator image Forge offers comes from a project that keeps publishing new builds, so the Android view keeps them current. Under Virtual devices, the "Updates and upgrades" row shows the last check, what is available, and three controls: Check now, Update and upgrade everything, and the daily mode. An **update** is a newer build of the same version from the same source: a Redroid tag rebuilt on Docker Hub (told apart by the image digest, not the date), a newer dated LineageOS system or vendor build from WayDroid-ATV, a newer revision of the same Google package in Google's SDK repository, a newer build of the same Mystic GSI port (the same source device) of a maker's Android, or a newer release of the ARM virtual machine from the android-lineage-qemu project. An **upgrade** is the same family for a newer Android: Redroid's next tag, LineageOS 25.0 (Android 18) when WayDroid-ATV publishes it, the same kind of Google package for a higher API level, or a maker's port for a newer Android. Each one has its own Update or Upgrade button, and the view says why an upgrade is not possible yet (Google already offers API 37 packages, but Redroid has no Android 17 vendor partition to run them on, so Forge cannot build them, and the view says so). An upgrade installs the newer version next to the old one; a device moves to it with the "Upgrade to" button on its row, keeping its apps and data, and Android migrates them on the next start the way a phone does after a system update (an app that does not survive that can be reinstalled).

What the checks read: Docker Hub's tag list, the SourceForge file feeds of WayDroid-ATV and Mystic GSI (which carry each file's date, size and MD5 sum; updated LineageOS files are checked against that MD5 sum, where the first builds were checked against SHA-256 sums written into `forge-vd-image`), `sdkmanager --list` for Google's repository, and GitHub's releases for the ARM machine. Every check has a time limit and runs in its own thread, so a slow network never blocks Forge. The daily mode (setting `vd_updates`, also on the Settings page) is **check** by default: once a day Forge checks and shows what it found. **install** also downloads and installs every update and upgrade, one at a time, inside the same memory cap as a download, never while a device of that version runs and never with less than 8 GB of disk free. **install-move** also moves stopped devices to the newest installed version of their family. **off** never checks by itself. Installs replace the image under a device's own data (a container device gets a fresh protected copy of the new image on its next start; an emulated ARM device boots the new system image from its own data disk), and nothing is deleted: a replaced ARM system image stays next to the new one as `system.img.replaced-<date>` in `~/.forge-ide/vd/arm/gsi/<version>/`, and Google's and WayDroid-ATV's downloads are kept, so you can remove old copies yourself when you need the disk. The updated recipes live in `~/.forge-ide/vd/catalog-overrides.json` (a newer file name for a port, a newer base machine, and every version added by an upgrade), which the scripts read as well, so `forge-vd-image` and `forge-arm-image` build the same thing Forge shows. Verified on 2026-10-18: the check found WayDroid-ATV's new Android 17 builds of 2026-10-17 (for Android 17 and Android 17 with Google apps) and revision 4 of Google's Automotive image; the Android 17 update was installed through the Update button (download, MD5 check, unpack and image build in about four minutes), Forge recorded it ("system 20261017, vendor 20261017") and the existing Android 17 phone then started on the new image with its own data, Ready after 26 seconds, with a system build date of 2026-10-17 over adb. The other two then went through "Update and upgrade everything" one after another: Android 17 with Google apps (its 1.5 GB download took an hour at the mirror's speed that morning, then the build) and Google's Automotive revision 4 (sdkmanager fetched the new revision and Forge rebuilt the image into a fresh folder in under five minutes), both recorded by Forge and both images carrying the new sources' dates.

## 17. The codebase index

Forge turns your code into embedding vectors with nomic-embed-text, a small embedding model, so codebase search and @codebase find code by what it does, not only by the words in it. Results are blended with keyword ranking.

- Indexing starts when a window opens and runs in the background at low priority. The status bar shows "Indexing 120/800" and then "Indexed". After the first time only changed files are indexed again.
- It pauses while a chat is running, waits when memory is short, and skips vendored, minified, generated and ignored files (in a git repository it follows `.gitignore`). A folder is limited to 4,000 pieces of code, newest files first.
- The embedding model runs in its own small llama.cpp server (about 250 MB), never in Ollama, so it never pushes Llama out of memory. It stops after two idle minutes.
- Settings, Codebase index shows the state and has Index now and Pause. Settings, Agent, Codebase index turns it off, also per folder.

## 18. Memories, rules, docs, hooks and more

- **Memories**: when you tell the agent something lasting ("always use tabs", "my server runs on Debian"), it offers to remember it. You see the memory, can edit it, and choose Save or Do not save. Memories are added to every chat, globally or for this project. Settings, Memories lists, edits and removes them.
- **Rules for the AI**: global rules and project rules in Settings (`~/.forge-ide/rules.md` and `.forge/rules.md`); `.cursorrules`, `AGENTS.md` and `CLAUDE.md` are read too. Cursor's rule folder works as well: Markdown files in `.cursor/rules` or `.forge/rules` with a small header. `alwaysApply: true` rules are always followed, rules with `globs` are added when a matching file is attached, and rules with only a `description` are listed so the agent reads them when they are relevant.
- **Docs**: Settings, Docs indexes a documentation site (up to 40 pages under the address you give) so you can mention it with @docs and the agent can search it with its docs_search tool. The ✕ moves an index to `~/.forge-ide/trash/docs`.
- **Hooks**: your own scripts that run at points in the agent loop: beforeSubmitPrompt, beforeShellExecution, afterFileEdit and stop. Configure them in Settings, Hooks (global or for the project). A hook gets the event as JSON on its input and the variables FORGE_EVENT, FORGE_ROOT, FORGE_FILE and FORGE_COMMAND. It may answer `{"permission": "allow" | "ask" | "deny", "message": "..."}`, and exit code 2 also means deny. For example, a beforeShellExecution hook can forbid certain commands, and an afterFileEdit hook can run a formatter.
- **Commands the agent may run**: Settings has an allowlist (commands that start with one of these run without asking) and a denylist (always refused, even with Auto-run on).
- **Source control**: branch, changed files, stage, unstage, discard (a copy is kept), diff against HEAD, Generate message, Commit, Pull, Push.
- **Notepads**: reusable notes; "Attach to chat" or @notepad adds one to a message.
- **MCP servers** in Settings: their tools run only after your approval.
- **Terminal Ctrl K**: plain English in, a command pasted into the terminal for you to run.

## 19. Working outside the project folder

The agent may read and change files anywhere on the computer with absolute or ~ paths, for example `/mnt/shared/Documents` (your Documents folder). With **External-file protection** on (Settings, Agent), it asks before changing a file outside the project; the approval card shows the path and the change. System files (for example in /etc or /usr) and keys (for example ~/.ssh) always ask, even with protection off. You can open any file yourself by typing its path in quick open (Ctrl P), for example `/etc/hostname`.

The Settings view has two tabs. **User** settings apply to every folder. **Folder** settings override them for the current folder only and are saved in `.forge/settings.json` inside it. ## 21. The GPU engine

**It starts by itself** (since version 1.15, setting "Start the GPU engine by itself", on by default): when the GPU engine is the chosen engine and it is not running, the Forge app starts it when you open Forge, when a message fails without it (the error says so, and the message gets a Retry button), and after the app was closed or updated. The start goes through the app's free-memory check every time, never happens next to another AI model (the vision model or a model loaded in Ollama), and a failed start is not repeated for three minutes. **Start it by hand**: Forge app, Settings, the GPU engine card, Start engine. The first start downloads the model weights once (4.9 GB). The app asks the VM to hand memory back, waits until the free-memory check passes, loads the model and reports "running". A notification with a Stop engine button stays visible. **When the Googlebook is short of memory** (since version 1.16): the status bar says so with the numbers, for example "GPU engine: waiting for memory (4.1 GB free on the Googlebook, needs 5.9 GB)", a message that fails for that reason says the same, and a reply that waits for the engine after the vision model waits up to ten minutes, as long as the app itself waits, with a status line every minute. Closing other apps on the Googlebook makes room, and the engine then starts by itself; the Terminal app must stay open, because it is the VM.

**Use it**: Use GPU engine for chats on the card, Settings, Engine, gpu, or pick it in a chat's model menu. Switching engines starts a fresh chat context.

**Its settings** (since version 1.17, all in Settings): **GPU engine: model** picks the Ollama model whose weights the app runs on the graphics; forge-coder is the tuned Llama 3.1 8B build, and qwen3.5:4b (Qwen3.5 4B, March 2026) is about half the size, so it needs about 3.8 GB free instead of 5.9 GB to start, generates about twice as fast per token on the graphics and has better tool use; the first start with a new model downloads its weights once. Measured on 2026-10-19 on the VM's processor (the GPU engine could not start that day): Qwen3.5 4B wrote a file, ran it and reported the output in three steps, 7.2 tokens per second of generation and 20 tokens per second of prompt processing, against Llama 3.1's 4 to 7 and 10 to 23 on the same processor. Forge's tool call tag is its own name (forge_tool) since version 1.17, because Ollama's parser for Qwen models intercepts the usual tool_call tag and drops the reply. **GPU engine: extra llama-server flags** are added to the engine's command line at every start. The default makes the chat template explicit, caps the engine's own prompt cache at 1 GB of RAM, uses one unified KV cache and turns on draft-free speculative decoding (ngram-mod), which guesses upcoming tokens from text the model has already produced; code and file contents repeat, so replies get faster, and a wrong guess costs little. If the engine refuses a flag and exits within 30 seconds, the app starts it again without the extras and says so in the engine log. The engine also keeps its cached prompt across a changed byte in the middle (cache reuse) and no longer skips its warmup, so the first reply after a start is not the slow one. **GPU engine: count the driver's held memory** is explained in section 22. **GPU engine: unload after idle minutes** (since version 1.18, default 30) makes the app unload the engine after that many minutes without a chat, so an idle laptop does not keep 3 to 4 GB of graphics memory busy; the next message starts it again by itself and waits for it (about 25 seconds with Qwen3.5 4B), and a message no longer fails with a Retry prompt while the engine starts: the reply waits and says what it waits for. The engine also runs with a micro batch of 256 tokens, which halves its scratch buffers on the graphics. A **memory guard** watches the Googlebook's free memory every two seconds while a Forge GPU process runs and stops the process when free memory falls under 700 MB or Android reports low memory, so the Linux VM is never the one Android reclaims.

**The prompt cache.** The engine reuses the processed prompt from the previous turn up to the first changed byte. Forge's system prompt (about 3,500 tokens with the tool list) therefore keeps everything that never changes first and the workspace outline, which is refreshed every 15 minutes, at the very end, so a refresh costs only the outline's own tokens instead of a whole cold prompt. The thought process a reply starts with is capped at three short sentences for the same reason: at six tokens per second, every hundred tokens of thinking is a quarter of a minute before the first action.

**Stop it**: the notification's Stop engine, or the card.

If the GPU engine is not running, a chat tells you so instead of loading the 5 GB CPU model by itself. Start the engine, or pick an Ollama model.

## 22. Memory safety

The Googlebook has 16 GB for Android, the VM and the models together. If it runs out, Android closes apps, and if it closes the Terminal app, the VM goes with it. Forge's rules:

- Every load on the GPU must pass the free-memory check, which keeps at least 2.5 GB free afterwards. It is never bypassed. The engine needs about 5.9 GB free to start, the 4B vision model about 3.6 GB.
- Only one model is on the GPU at a time. The vision model and Llama take turns.
- When a GPU model stops, the graphics driver keeps its memory for reuse, and Android does not show it as free. Measured on 2026-10-19: after the engine and the vision model had run, the driver held 5.5 GB; with every other app closed, Android still reported only 3.7 GB free, and a vision model that then started took 1.4 GB straight out of the held memory. Forge accounts for that only within 15 minutes of its own GPU use, and the status bar says "GPU engine: waiting for memory" with the numbers. Restarting the Googlebook clears it. The setting **GPU engine: count the driver's held memory (percent)** (default 0) lets the free-memory check also count that share of the held memory, which Forge measures as the memory no counter of Android explains, minus what was unexplained before Forge's first GPU process of this boot; the memory guard above backs it. Leaving it at 0 keeps the check on what Android reports as free; it is your decision, because it is the one setting that lets Forge load a model into memory Android does not report as free.
- **What Forge holds on the Googlebook, measured on 2026-10-19 while a screenshot was being described**: the Forge app process 92 MB (300 MB resident with its threads), one WebView renderer per open Forge window at 150 to 300 MB each (the page itself holds only about 20 MB of script data; the rest is the browser engine, the editor and the terminal), the GPU engine process 154 MB plus about 3.7 GB of graphics memory for Qwen3.5 4B with its context, the vision model about 3.5 GB of graphics memory while it works (taken from the memory the engine's pause frees), and the Linux VM about 2.8 GB resident on the Googlebook. The VM's file cache counts against the Googlebook until the VM hands it back; since version 1.18 Forge hands it back from 700 MB on whenever the Googlebook reports under 3 GB free. Every open Forge window costs a renderer, so close windows you do not use; since app 1.11 a closed window also leaves the Recents list.
- In the VM, the CPU model loads only with about 5.8 GB free in the VM and, when the Forge app can report it, on the Googlebook too. A watchdog unloads models under 320 MB free in the VM. Switching a chat to a different Ollama model is refused when there is no room for it.
- The helpers check memory before they start, and helpers that run inside a memory cap start only when the Googlebook has the cap plus its 2.3 GB reserve free, so even a helper that grows to its cap cannot push the Googlebook below the reserve. The caps: the debugged program 1 GB, a notebook kernel 1.5 GB, the Kotlin language server 1.8 GB (2.4 GB in an Android project or with a full Gradle import, 3.2 GB for both), the Java and Rust language servers 1.5 GB, and builds whatever is free above the reserve, up to 2 GB. Helpers stop when they are not used, and the embedding server stops by itself if the Forge server ever stops.
- The command palette has Unload the model from memory.

- **Virtual devices** each run inside a hard memory cap (2.5 GB for Android 11 to 16, 3 GB for Android 17) and a limit of 8,192 threads (Android with Google's apps needs more than Podman's default of 2,048, and its system process crashed without them; the VM allows about 62,000 in all). The memory shown for a device is Android's own memory; the file cache in its cap is given back whenever something needs it and start only when the Googlebook has the cap plus 2.3 GB free. In practice that means one device at a time next to Forge, and not at the same time as the Llama model. A watchdog for each device returns the VM's file cache to the Googlebook when it falls under 3.8 GB free, and stops the device under 2.9 GB free, when it cannot read the free memory for two minutes, or after three hours without use. Downloads and image builds run inside a memory cap too.
- **Android shares the VM's kernel.** In a container, Android runs on the VM's own Linux kernel, and Android's startup was written for a phone that Android owns. Left alone, it would change the whole VM. Forge has two layers of protection against that, together called the VM shield.
  - **Protected images.** Forge runs every virtual device from a protected copy of its Android image, which it builds by itself in a few seconds the first time (Podman lists them as `localhost/forge-shield`). In that copy, Android's startup scripts leave out every line that would change the VM: kernel settings for the whole VM (memory overcommit, memory watermarks, a kernel panic when a task hangs, SysRq, performance counters and the console log level), the owners of the kernel's files (Android's "system" user has the same number as your own account, so it could otherwise suspend the VM or install a SafeSetID policy that breaks `sudo`), handlers for ARM programs, kernel trace buffers, swap, and the livelock daemon `llkd`, which can crash the kernel on purpose. Exactly what was left out is listed in `~/.forge-ide/vd/shield/*/removed.txt`. Containers also cannot reboot or replace the kernel, load kernel modules, use hardware ports or change the clock.
  - **The Forge Android guard** (`forge-android-guard`, a small root service with a 128 MB memory limit). Android's own shutdown signals every process in the VM, remounts its disks read-only and can crash the kernel, so Forge always stops devices from outside, and the guard ends any Android that starts to shut down by itself within milliseconds. The guard holds a kernel wake lock, so Android's suspend service can never put the VM to sleep, and a secret memory handle, which makes the kernel refuse to hibernate. While any Android runs (WayDroid too) and for a minute after, it compares the VM's kernel settings and the owners and modes of the kernel's files with a reference taken while no Android was running, and puts back anything that changed, within about two seconds. Some changes come from Android's programs and not its scripts (its init, for example, always restricts `/proc/cmdline`, which the Terminal's display setup reads when a shell starts), and the guard catches those at the moment Android's init starts. It also clears any SafeSetID policy, switches off Android's handlers for ARM programs and warns you if an SELinux policy was ever loaded.
  - **Google's own builds** (Wear OS 6, Google TV 16 and Android 16 with Google Play) start with Redroid's container-ready start program and SELinux library, so Android's SELinux policy is never loaded into the VM's kernel, and they get the same device-mapper lock as Android TV 16 (see Google's own Wear OS, Google TV and Pixel-style Android in section 16).
  - **Device-mapper and disks.** Android's package manager creates device-mapper entries named after its packages, and those live in the VM's shared kernel, where they would stay after the container stops and keep the next Android's packages from mounting. The Redroid and Android 17 images have no device-mapper device to do it with. In Android TV 16, `forge-init` puts a locked placeholder in its place, so Android mounts its packages straight from loop devices, which the kernel releases by itself, and it copies none of the VM's disks into the container. If such entries ever exist, the guard warns about them.
  - The Android view shows "VM shield on" and how many changes the guard put back in the last 15 minutes. Its log is `journalctl -u forge-android-guard`.
  - **About SELinux:** this kernel has SELinux built in but no policy loaded. Android's normal startup loads its own policy, which would put the whole VM under Android's rules. The images Forge uses are built for containers and skip that step, and the guard ends any Android that starts to load a policy. Google's own emulator images do not skip it, which is one reason Forge never runs them in a container.

Do not run Waydroid, a second model or a large build at the same time as a model.

## 25. Troubleshooting

- **Waiting screen**: the VM or server is not up. Open the Terminal app, wait, Retry, or `forge-ide status`.
- **Ollama offline**: `sudo systemctl restart ollama`.
- **Slow first reply**: the model is loading or a cold prompt is being processed. Follow-ups are fast.
- **The engine waits for free memory**: close heavy apps. If it keeps waiting after GPU work with everything closed, the graphics driver is holding Forge's earlier GPU memory (section 22): restart the Googlebook, or set "GPU engine: count the driver's held memory" in Settings.
- **"The vision model is waiting for memory" while the engine runs** (fixed in app 1.9): the engine pauses for the vision model, and the app did not record the pause as a stop, so the vision model's memory check got no credit for the memory the pause had just freed. Now it does, and a vision failure in the chat names the app's own reason (for example the memory guard) instead of only "stream interrupted". Verified on 2026-10-19 with the engine running and 3.3 GB visible: a screenshot was described in 55 seconds (6 s loading, 10 s looking, 49 s writing 242 words with the 2B model).
- **A screenshot gets only text recognition**: the vision model did not fit in free memory, or the Forge app is not running. The panel under the image says why.
- **"Not enough free memory"** for the CPU model or a helper: close other programs, or use Unload, then retry.
- **No suggestions or hover in the editor**: the language server for that language is not installed (`install-extras.sh lsp`), memory was short when the file opened, or Language servers is off in Settings. Reopen the file after fixing it.
- **The Terminal app says the Linux VM is low on memory and suggests more RAM**: the Terminal counts every out-of-memory stop inside the VM, including the deliberate ones, when a helper reaches its memory cap and is stopped. Helpers are sized to stay well below their caps, so this should be rare. If it happens, the helper's feature stops (a build fails, or code intelligence for one language ends), and nothing else is affected. Reopening the file or running the build again with more memory free continues.
- **"Not enough free memory" for a build**: a build needs at least 1.5 GB above the Googlebook's 2.3 GB reserve (about 3.8 GB free). Close other apps, use the GPU engine (which takes the model out of the VM), or unload the model.
- **The Googlebook is missing in the Android view**: click Connect this Googlebook. If that fails, check that Wireless debugging is on. Its address changes after sleep, and Sleep Guard publishes the new one.
- **A new terminal shows `grep: /proc/cmdline: Permission denied`**: an Android changed that file's mode. The guard puts it back within seconds, and the display setup works the same either way on this VM. If it stays, check that the guard runs: `systemctl status forge-android-guard`.
- **Google's device lab says you are not signed in, or that a project is missing**: run `android auth login` in a terminal, and enter a Google Cloud project with device streaming enabled. `android device remote projects` lists them.
- **A download of a maker's system stopped**: the Googlebook's Wi-Fi re-joins drop the Linux VM's network for a few seconds (every screen wake does this). Downloads resume by themselves and retry for ten minutes; if one still ends, click Download again and it continues from where it stopped, because a download is written to a part file and renamed only when complete.
- **A virtual device does not start**: the message says why. Usually memory is short (stop another device or unload the model), the Android version is not downloaded yet, or the Forge Android guard is not installed (run `guard/install.sh` in the Forge folder once). Notices at the top of Virtual devices say when the watchdog or the guard stopped a device. A device that has not finished starting after 4 minutes is stopped, so it does not keep its memory. If Android TV 16 starts but Forge cannot reach it, check `sudo systemctl status forge-vd-dhcp` (the network service for TV devices) while it starts.
- **The VM shield warns about device-mapper entries named after Android's packages**: an Android created them in the VM's kernel, where they stay after the container stops and keep the next Android's system packages from mounting. They hold no data. Restarting the Terminal app clears them (stop the virtual devices first). Forge's images no longer let Android create them.
- **A paired device does not connect**: pairing and connecting use two different addresses on the device's Wireless debugging screen. The pairing code expires after a minute, and the device must be on the same Wi-Fi.
- **Kotlin code intelligence does not start**: it needs 4.1 GB free on the Googlebook (4.7 GB in an Android project; with the full Gradle import 4.7 GB, or 5.5 GB in an Android project). Forge says so once; reopen the file when more memory is free. The first start in a project takes longer while it reads the project and the libraries.
- **The microphone does nothing in the app**: allow the microphone for Forge in Android's settings (Apps, Forge, Permissions).
- **The index stays at "Index waiting"**: memory was short; it continues by itself when memory is free again. Settings, Codebase index shows the reason.
- **A notebook says the kernel stopped**: a cell used more than 2 GB of memory, or the kernel was idle for a long time. Run a cell to start a new kernel; variables need to be computed again.
- **The agent seems confused by earlier parts of a long chat**: start a new chat (Ctrl N), use /reset, or Restore checkpoint on an earlier message.
- **A bad agent change**: Undo in the editor, Revert all under the reply, Restore checkpoint, or AI Changes.

## 26. Updating Forge

Edit the code, then `forge-ide restart`. For the app, `android/build.sh` and `adb install -r android/Forge.apk`. For the model file, edit `model/Modelfile` and run `forge-ide model`. For the optional parts, run `install-extras.sh` again with the part's name (`lsp`, `debug`, `docs`, `voice`, `index`, `android` or `rust`).
